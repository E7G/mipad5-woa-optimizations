# Android kernel / WOA power crosswalk (2026-10-28)

This is a **source-and-address comparison**, not a Windows driver patch. Android DTS descriptions cannot be copied into ACPI or used as Windows power settings. Android kernel source is pinned to [AwakenOS nabu commit `2f84d28`](https://github.com/AwakenOS-Devices/android_kernel_xiaomi_nabu/tree/2f84d28068bd3c8b9ec4281323ce65d650694efa); our WOA comparison uses the currently deployed nabu ACPI DSDT and the tablet's local SleepStudy. No Android source or private ACPI dump is redistributed here.

The ACPI `GPU0` `_DEP` list includes `MMU0`, `MMU1`, PEP and other providers; `MMU0` depends on `MMU1`. These declarations are **device startup dependencies**, not a full runtime power-state graph. [Microsoft's PoFx component model](https://learn.microsoft.com/en-us/windows-hardware/drivers/kernel/component-level-power-management) requires the owning driver to idle components correctly. The [graphics runtime component definition](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/d3dkmddi/ns-d3dkmddi-_dxgk_power_runtime_component) likewise does not make a registry override a substitute for a KMD fix.

Closer review of the **deployed** DSDT (SHA-256 `6958CC6F88CF083B4BCD5A4F05CF32538BEA98E84E96BE4861629ED9F92560AE`) PEP method `G0MD` shows that **GPU component 0's F1 transition** includes `mdss_core_gdsc`, display clock/bus votes, PMIC votes and TLMM GPIO `0x72`/`0x73` (decimal 114/115). The Android nabu DTS assigns GPIO 114/115 to the panel ENP/ENN regulators. This is a stronger hardware crosswalk than matching GPU names alone. It also explains why forcibly pushing the whole graphics device idle is a high-risk experiment: that transition affects the actual panel power path. It does **not** prove the failed wake was caused by any one GPIO or sequence; the graphics driver and PEP transition order still need a trace.

The Android panel ENP/ENN nodes each specify a 233-microsecond regulator ramp delay. `G0MD` has no explicit `DELAY` action, although this ACPI table uses that action elsewhere. Whether the WOA display KMD or PEP provides equivalent sequencing is **unknown**. This is a targeted source-review lead, not sufficient evidence to insert a delay or flip the rails: first capture a successful normal wake and the previous failed forced-idle path, including rail/GPIO order where possible.

## Next reproducible gate

1. Collect `powercfg /sleepstudy /xml` after an ordinary, battery-only, manually initiated standby. Run `python tools/summarize_sleepstudy.py sleepstudy.xml` locally; **do not upload the raw XML**. Compare GPU0 components 0/6/7, MMU0 and MMU1 across sessions.
2. Before any new patch, obtain a trace that ties GPU0 display-component activation/idle callbacks to MMU0 device activity. The current SleepStudy only shows correlation, not the caller or rail power.
3. Source-level change belongs in the owning WOA graphics/SMMU/PEP driver or ACPI only after the missing transition is identified and rollback is validated. The public WOA graphics/SMMU binaries are not source-level implementations; no safe blind replacement is proposed here.

No new Windows driver, boot image, ACPI table, registry value, or standby policy was changed for this crosswalk. Whole-system DRIPS is still unproven to improve.
